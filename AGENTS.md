# AGENTS — инструкция для ИИ-агентов

Прямое руководство для ИИ-агентов, работающих с репозиторием appboo.
Пользователь говорит «выложи приложение» и прикладывает файл(ы) — далее
действовать по этому документу, не изобретая собственных схем. Полные
контракты и конвенции — в [CONTRIBUTING.md](CONTRIBUTING.md); здесь —
практический порядок действий.

## Главная идея

Выкладка приложения — короткая задача: разложить файлы, добавить
метаданные, прогнать два скрипта, доставить ОДНИМ коммитом. Доставка «по
частям», временные ветки `tmp/**` и ожидание воркфлоуов для обычной
выкладки НЕ используются (резерв — только для файлов, которые физически не
проходят через API одним куском).

## Порядок действий

1. Проверь входные данные: должен быть файл с точкой входа `.html`
   (обычно `index.html`). Если его нет или задача непонятна — см.
   «Когда переспрашивать», ничего не начинай.
2. Придумай имя папки: kebab-case `^[a-z0-9]+(-[a-z0-9]+)*$`, короткое,
   по названию приложения (например `color-lab`), уникальное в `apps/`.
   Имена существующих (легаси) папок не трогать.
3. Разложи файлы:
   - код приложения → `apps/<имя>/src/`, точка входа — `src/index.html`
     (если входной файл один, но называется иначе — переименуй);
   - `apps/<имя>/meta/meta.json` — по шаблону `docs/meta.template.json`;
   - `apps/<имя>/meta/icon.svg` — монохромный штриховой SVG
     (`viewBox="0 0 24 24"`, `fill="none"`, `stroke-width="1.7"`,
     `stroke="#ffffff"`; полный гайд — в CONTRIBUTING.md);
   - `apps/<имя>/meta/screenshots/screenshot-1.webp` и
     `screenshot-2.webp` — 1280×800, ≤300 КБ, WebP q≈85 (пиксель-арт —
     lossless); оба пути — в массиве `screenshots` meta.json.
4. Прогони из корня репозитория:
   - `node scripts/normalize.mjs` — впишет запись в `catalog.json`
     (дату `added` проставляет он сам; каталог руками не редактируют);
   - `npm run validate` — MUST-нарушений быть не должно; SHOULD-долги
     лучше закрыть сразу, но они не блокируют.
5. Доставь всё ОДНИМ коммитом (см. «Доставка») и отчитайся.

Запрещено: редактировать `catalog.json` руками; трогать плеер `index.html`
(допустимые пределы — в CONTRIBUTING.md); коммитить файлы по отдельности;
публиковать приложение без точки входа `src/index.html`.

## Недостающая информация — добыть самому

Пользователь мог не дать название, описание, теги, иконку или скриншоты.
Сначала добудь их сам, это нормальная часть работы:

- название — из `<title>` приложения или из слов пользователя;
- описание — одна фраза о сути приложения по его содержимому;
- теги, `languages`, `platform` — по содержимому (игра/инструмент/…,
  `ru`/`en`, `desktop`/`mobile`/`both`);
- `ai` — нейросеть, генерировавшая приложение, если это известно;
- иконка — простой монохромный штриховой SVG по теме приложения;
- скриншоты — снимки экрана работающего приложения (headless-браузер),
  2 шт., конвертированные в WebP.

Если что-то добыть не удалось — переспроси одним коротким списком, что
именно нужно (например: «не могу снять скриншоты — приложи два PNG
1280×800 или разреши опубликовать без них»). Молча публиковать неполное
можно только после явного согласия пользователя на «быстрый дроп»
(MUST-минимум из CONTRIBUTING.md).

## Когда переспрашивать — не выдумывать задачу

Остановись и задай короткий уточняющий вопрос, если:

- не прикреплён ни один файл с точкой входа `.html`;
- непонятно, какое именно приложение выкладывать (прикреплено несколько);
- непонятен порядок (несколько приложений, зависимость между ними);
- просьба звучит как выкладка, но задача иная (обновить, заменить,
  удалить существующее приложение, поправить плеер).

В этих случаях НЕ начинай действовать по своему усмотрению и не выдумывай
задачу: вопрос — ожидание ответа — действие.

## Доставка: приоритет способов

Все изменения доставляются одним коммитом. Способы по приоритету:

1. **Пуш в main одним коммитом** — основной способ, если у агента есть
   доступ на запись: собрать изменения, закоммитить, запушить в `main`.
2. **Pull Request** — если прямого пуша нет или пользователь просил
   ревью: ветка + PR в `main` со ссылкой в ответе.
3. **Патч для `git am`** — если API недоступен: единый mbox-патч
   (`git format-patch`), файлом в ответе.

О принятом способе явно сообщи в ответе вместе с мини-инструкцией, что
пользователю делать дальше:

- «Запушено в main одним коммитом: `<ссылка на коммит>`; приложение:
  `<ссылка на приложение на GitHub Pages>`»;
- «Создан PR: `<ссылка>` — посмотри и вмержи»;
- «Патч: примени `git am <файл>.patch` из корня репозитория на свежем
  `main`».

Воркфлоу `apply-tmp-patch` (ветки `tmp/**`) — крайний резерв для правок,
которые не проходят через API одним куском (например, огромный
`index.html` плеера). Для выкладки приложений не использовать.
